# 联机同步 V5：任务分流与锁等待实测

2026-10-29。本地候选，未部署、发布、提交或推送。云端仅使用一次性隔离副本，正式 Data 只读；既有工作区修改保留。

## 结论与验收

已实施个人任务锁外规则计算、版本复核提交、有界等待及优先处理、非阻塞完成通知、无计时更新时的快照读取分流，以及制作面板剩余的一次重复列表构建修复。数百毫秒的获取世界锁等待已有直接测量证据，不能再仅归因于网络。**世界写事务仍整段持锁执行原规则宿主，代码侧和端到端目标均未全部达到，不能称为联机性能已验收。**

代码侧目标：服务端业务 P95≤80ms、客户端命令应用 P95≤20ms；interact/craft 双人服务端专项目标≤150ms。端到端目标：正式公网直连确认 P95≤150ms。以下逐玩家、逐操作列实测，不能以合并分位数掩盖某个玩家的尾延迟。

## 测试条件与可比边界

Godot 4.7.2、真实 OpenGL 窗口、默认1280×720，同一初始世界（88个建筑）、相同测试账号初态和动作脚本；单人、双人分别进行移动、拾取、移格、制作、建造、争抢、后台快照及新进程恢复。普通操作每人计划30次，具体成功数及失败次数分别保留。移动和两人走位受真实调度影响，不能保证每个动作到达顺序完全相同。

修改前本轮 P95 明显高于上一轮：云机非独占，观察到负载约2.2–2.6，正式游戏进程同时有约56% CPU活动，未停止或修改正式进程。这个干扰限制了性能改善的因果强度；只比较本轮固定初态的前后，不把上一轮322ms与本轮数据拼接。每类操作约6个成功样本，P95是线性插值，不是长期稳定性证明。

初版 after-*-v5 与最终 after-*-final-v5 均留在 measurements.md/summary.json，不挑较快的一轮替代最终结果。最终版新增“轻事务首次状态捕获也预留优先权”；它不能抢占已经持锁的世界事务。

性能矩阵完成后，补充检查又修正了同ID制作重试误走重事务、权威取消标记及忙快照误报同步失败；这些边界修订另跑完整规则及真实取消/断线专项，没有重复整张性能矩阵。故表格对应final性能批次，消息大小不包含后来新增的取消布尔标记，不能宣称这些小修订已有新的整组P95。source-hashes.json记录交付候选源码，不是早先性能批次逐文件哈希。

## 完整链路与已确认瓶颈

`network_game_route → network_game_world.sync_server → Network.call_api → 独立 HTTPClient → TLS Handler → Service.handle → 原规则宿主 → 持久化 → 响应编码/压缩 → 主线程 HTTP 轮询/解码/解析 → 帧末权威应用 → UI回调 → frame_post_draw`。关联用同一 request_id；重试保留原ID和幂等回执。

1. 原世界写路径在共享 RLock 内执行规则宿主IPC；到期世界计时还会串行推进另一名玩家。普通拾取和建造确实可能携带这部分工作。个人库存上一轮虽锁外计算，首次捕获、提交以及完成后通知仍可能被其他世界事务拖住。本轮分别计量获取锁、业务和IPC，排除了“只有网络慢”的解释。最终双人A最大建造请求95f83114d4a69b1862ad59e84ce5aa87确认998.83ms，其中业务886.57ms：获取锁361.76ms，两次原规则IPC分别253.16/176.66ms，保存19.86ms，其余75.12ms。调用顺序是先推进另一玩家，再执行本玩家请求；这比链路残差大得多。
2. 徒手制作开始/取消、个人指引和离开工作台标记现在复用原 ItemService 规则，在无世界场景的个人宿主处理；带加工台、动态解锁、战斗/睡眠/钓鱼等依赖时保留原路径。制作完成仍在原权威世界计时中重新校验、扣料和发物，不提前发放。额外扣除共享计时中“任务开始前”的区间，避免新任务被过早推进。
3. 提交先比较个人版本和依赖快照；每次锁尝试2ms，服务器总等待预算200ms，冲突最多3次重算。仍不能提交则返回command_pending，客户端8ms后保留队头和同一请求ID重试。优先登记覆盖捕获到提交，完成通知改成非阻塞。它是短锁内的比较提交，**不是无锁CAS，也没有消除首次捕获和已持锁事务的等待**。失败保存回滚角色及回执。
4. 已进入世界、选中格不变、无需世界计时的game_snapshot，尝试直接读取已提交快照；忙时返回snapshot_pending交给后续轮询，避免把只读快照挂在重事务后。需要推进世界或改变选中格时走原事务。代码没有独立的只读空间查询RPC；拾取/建造的距离与碰撞校验属于权威写操作，不能脱离其事务并发后直接信任。三类分流覆盖现有安全分支，世界写事务本身仍未拆开。
5. 本轮没有继续压缩消息、改缓存容量或新增预取。逻辑响应仍使用既有组件增量协议，任务响应还包含权威快照；客户端任务确认仍执行完整状态应用，应用开销仍可能超过20ms。网络轮询、解析仍在主线程，帧末队列不等于网络线程。

## 计时方法与链路环境

没有直接相减客户端单调时钟和服务器单调时钟。客户端测请求提交至收完；服务器用自己的perf_counter_ns测接收、业务、获取锁、响应准备与写出，并回带Server-Timing时长。两端仅比较各自的持续时间。request()处是HTTPClient提交时刻，非抓包观察到的网卡发包时刻；字节数是实际HTTP应用消息体，不含TLS/TCP帧开销。

HTTP等待减去同请求“服务端接收到响应准备好”的时长得到往返残差，仍包含客户端帧轮询、SSH、上下行与未观测的连接/调度开销，不能称为纯网络单向耗时，也不能推出服务器接收前没有排队。安静小包探针与真实命令残差分开列于measurements.md/attribution.json。

隔离副本公网28871端口不可达，未改防火墙或正式入口。本轮使用SSH转发TLS作前后对照。对现有正式公网TLS入口只做无凭证拒绝请求参考，20个热连接样本P50/P95/max=39.64/73.99/555.16ms；它不是新代码的公网业务验收，存在最大值尖峰。此前131ms是某轮应用往返残差，**不是物理硬地板**；正式公网直连150ms目标本轮无法判定，也不能据此免除当前代码业务目标。

## 一致性、恢复与检查

交付候选完整37项原规则及个人事务检查通过，包括个人任务开始/取消/指引/加工台回退、制作前区间排除、同ID任务重放、保存失败回滚及取消重试；新增4项锁递归Condition、有界提交、非阻塞完成通知和忙快照延后检查通过；既有TLS增量/丢失基线/旧协议检查1项通过。修正过程中出现过宿主脚本分支放置错误导致启动失败，已经纠正并重跑受影响检查；未将失败运行计作通过。最后补了缺失计时时钟时的防御访问及取消与已完成任务的权威区分，边界由本地检查和真实窗口专项覆盖。

consistency.json逐人核对材料与产出守恒、争抢仅一个获胜、双人建筑ID一致、新进程恢复库存装备及建筑；同时记录交叉客户端请求重叠数量，确认两人确有同时操作。未见预测移动冻结帧；队列峰值只是本脚本观察，不能证明长时间无积压。

制作在途关闭进程后，以新进程登录恢复，确认材料只扣一次、产物只发一次、99.9%控件不提前满格，恢复后继续等待无重复奖励；交付候选另加真实窗口的活动制作取消，确认取消显示失败原因、进度归零、材料不扣、产物不发。配方1.5秒，重新启动通常已完成，因此没有充分覆盖“重连后任务仍长期在途”或服务器崩溃。原始专项结论见craft-recovery.json。

# 联机同步 V6：削减世界事务持锁工作量

2026-10-29。本地候选，未部署、发布、提交或推送；未修改正式玩家存档。

## 结论

原路径确实把其他玩家计时与当前命令串在同一个共享锁里。本轮已移除：计时由独立规则宿主计算并比较提交；普通写操作只执行自己的原规则，IPC 在共享状态锁外执行，保存成功才确认。固定服务端测试中，触发计时的空间请求由两次 IPC 降到一次：before 的 180 个空间请求中 164 个一次、16 个两次；after 的 180 个均一次。不是所有旧请求都执行两次。

**最终真实窗口双人混合确认 P95 从 383/376 降到 280/272 ms（约27%改善）；单人从238变为246 ms，未改善。150 ms 未验收，不能宣布联机延迟解决。** 共享锁缩短以后，原规则 IPC、规则通道互斥、计时冲突重算、D 盘同步落盘和客户端应用仍有成本。下列结果完整保留回退，不能以服务端压测代替窗口验收。

## 实际修改

- `tools/network/server.py`：世界计时从 HTTP 命令/快照路径移到独立后台任务；规则计算使用私有候选，版本/依赖相符才提交。玩家写操作在共享状态锁外运行原规则，短锁内复核、同步保存、失败回滚；回执保持幂等。
- 同文件：计时冲突不消耗时钟；持续写入两次冲突后，在共享状态锁外预留规则通道重算，防止计时永久饥饿。它仍可能使世界命令等待，不能称为完全消除争用。普通移动保留，复活/击退等规则位移优先；只有规则未改变库存且无制作任务时，才合并并发背包变化。
- 已有初始化/释放和战斗连锁仍可能多次 IPC，不在“一次”保证内。首次进入时恢复原规则权威状态，避免第一次交互才等待场景。两个必要宿主在实际世界加载阶段并行准备并等待就绪；早期只排队、不等待就绪的实验已撤回。未增加区块预取。
- `tools/network/game_host.py`、`scripts/network_game_worker.gd`：记录真实跨进程 IPC 请求字节、编码、恢复、场景等待、计时和操作/快照耗时。服务器补充规则通道等待、捕获、保存编码/数据库耗时；诊断写文件使用独立锁，避免 Windows 并发追加损坏。
- `tests/test_network_world_v6.py`：12 项事务/计时回归；更新原规则服务测试的独立计时预期及旧 TLS 测试替身配置。未修改客户端应用或面板实现。

## 对照条件

同一 Windows 电脑、Godot 4.7.2、16 逻辑 CPU、同一 88 建筑隔离初态。before 是本轮开始时冻结的源码（含计时探针），不是 Git HEAD，也不是历史云机结果。after 使用本轮事务修改；最终窗口候选是 after-ready（含首次状态恢复、场景就绪和双宿主加载修正）。保留 after-final、after-warm、after-motion、after-init 等中间结果，不能择优作为最终数字。

纯服务端测试直接调用真实 `Service.handle` 和真实 Godot 原规则，固定 1/2 调用方，每人每类 30 次成功；同时起跑，单人阶段仅一人在线；计时宿主已预热且计时从统一初态开始，世界恢复/补料在计时区间外，限流关闭，制作取消不计入开始请求。每次请求唯一 ID；这组不经过 HTTP/网络/渲染，数据库在系统临时目录 C 盘。

窗口组是真实 OpenGL 1280×720，客户端与 TLS 服务均在本机；数据库在本项目 D 盘隔离目录。包含持续快照、移动中拾取/制作/建造、同对象争抢和新进程恢复。不是 SSH、公网或云机测试；旧脚本结果中的 SSH scope 字符串是历史常量，本轮以 `run_local_native.py` 的 127.0.0.1 配置为准。

C/D 两类结果只在各自前后比较。Windows 没有本轮 Linux load average，记录整机 CPU 百分比；不能声称独占负载完全相同。

- before API：整机 CPU 平均 19.9%，范围 9.0–42.8%；用时 50.2 s。

- after API：整机 CPU 平均 22.1%，范围 10.3–48.5%；用时 194.6 s。

## IPC 与消息开销

IPC 是 Python→独立 Godot 进程的私有回环 TCP，不是进程内调用。该通道继续可靠传输，未替换为不可靠 RPC/UDP。空间命令仍传完整规则输入；本轮没有假称已经实现实体级增量规则接口。

## 延迟分解与持久化新证据

从最终双人批次选一个两端日志可完整关联的真实成功请求，按各端单调时钟分别求持续时间；不跨机器相减时间戳，不把链路残差称为纯上行或公网 RTT。下面选取有完整关联记录的较慢请求，不能冒充所有样本各段 P95 的相加。

操作 `interact`，确认 270.5 ms，首帧 278.9 ms；请求/响应 2290/11726 B。

同一次请求的耗时归因（数值可相加，残差包含传输和系统/回调调度）：

```mermaid
flowchart LR
  A["发出前排队/编码 2.5 ms"] --> B["服务器 210.0 ms"]
  B --> C["传输/调度残差 13.6 ms"]
  C --> D["解压/解析 6.4 ms"]
  D --> E["主线程排队/应用 38.0 ms"]
  E --> F["确认 270.5 ms"]
```

|阶段|ms|边界|
|---|---:|---|
|客户端发送→解析完|229.9|包含服务器及往返/回调|
|服务器接收→发送完|210.0|发送→解析区间内的服务器段|
|其中业务|177.2|包含规则通道等待、规则计算和持久化|
|其中共享状态锁持有|57.6|业务子集，不能再次累加|
|客户端解压/解析|6.4|发送→解析完的子集|

|确认→真正显示|8.5|frame_post_draw|

这是一条可关联请求的分段，**不是各段 P95 的加法瀑布图**。缺失的传输/调度段只可作为同请求时长的残差，不能据此认定网络有问题。

首次交互场景等待的证据：修正前同请求 IPC 1239 ms，其中场景等待 1092.7 ms、恢复 96.6 ms、操作/快照 6.2 ms、编码 1.6 ms。根因是首次初始化快照提前返回存档、未恢复命令规则宿主；修正为加载期先恢复，并等待几何/物理就绪，普通后续快照仍不推进规则。after-init 真窗口单/双人最大确认约278/427/449 ms，秒级首次交互退化已消除。最终含双宿主就绪的结果以 after-ready 表为准。初始化耗时没有消失：本轮 character 加载单人20.10→28.30秒；双人A/B分别23.65/20.50→21.22/24.43秒（每人仅1次，不报加载P95）。后台独立宿主增加启动和内存成本，单人加载存在回退，尚需优化。

保存探针已区分 JSON 编码和数据库事务。真实窗口出现约 2 ms 编码、约 30–100 ms 数据库写入的请求；不是把这部分算成规则 IPC。对同样约 278 KB 载荷、SQLite WAL + FULL 的独立 30 次持久化：C 盘临时目录 P50≈1.6 ms、最大≈4.8 ms；D 盘项目目录 P50≈36.7 ms、最大≈122.6 ms（原始 D 盘样本 persistence-probe.json）。这是本机存储差异证据，不能外推为云机磁盘已确诊。

仍保留同步持久化后确认，未为了数字改用 NORMAL/OFF 或提前成功确认。尚未实现异步快照写队列/增量 WAL，完整保存仍在共享状态锁内；这是明确未完成项。

旧版并发追加 trace 有部分行损坏，汇总器单列 invalid_wire_lines，不用于缺失请求的归因；客户端独立原始计时和 API 矩阵不受该文件损坏影响。本轮已给 trace 追加独立锁，最终窗口日志损坏行数为 0，避免继续丢证据；不可声称历史 trace 完整。

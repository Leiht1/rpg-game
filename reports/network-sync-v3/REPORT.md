## 已确认的问题与修复

1. **每条普通命令都返回完整玩法状态。** `server.Service.dispatch → Gameplay.apply → GameHost.execute → network_game_worker.execute → ItemService.snapshot → Gameplay.snapshot` 返回完整状态；HTTP 层再次 JSON 编码、gzip，客户端解压、JSON 解析，再执行 `network_game_world.apply_snapshot → ItemService.load_state`。命令权威提交后，客户端仍等本条回复的状态恢复结束才显示结果。HTTP 命令与后台快照已有独立连接，没有证明同一连接里命令被大快照挡在前面；但两者仍竞争服务端事务/规则宿主和客户端主线程。
2. **身份初始化重复传递玩法存档。** resume、character 原来各携带约 263 KB JSON 世界/人物数据，随后又请求初始玩法快照。新客户端协商 `sync_init=1` 后，身份回复仅带进入场景所需世界字段、人物元信息，初始权威玩法状态仍完整获取一次；旧客户端保持原格式。
3. **大量未变化的状态重复验证。** 主线程原来每次都验证探索、商人、钓鱼、动物、营地和环境；遗物每件物品甚至重新构造 40 格库存。成功验证后的相同内容现在复用结果；发生变化仍走原验证。建筑复用成功验证结果时，仍把缓存的独立物品 ID 与本次背包/掉落交叉检查，不能借缓存复制工具。没有跳过权威验证或把客户端输入当作可信状态。
4. **普通背包移格依赖无关的世界计时推进。** 当前没有战斗时，移格/拆分/删除/整理不再抢先推进所有在线角色。保留原世界时钟，下一次满足原节流条件的快照补进完整经过时间；装备、使用物品、战斗与空间交互维持原路径。
5. **已改为组件增量传输。** 客户端提交已持有的组件摘要，服务器只传改变的顶层组件。客户端针对每次请求捕获独立基线合并；丢包、并行回复及重连不会偷偷推进服务器端基线。缺字段按最新摘要表删除；旧客户端仍收完整状态。**这不是实体属性级补丁**：变动的背包仍是整份 40 格、变动的建筑/动物组件内部仍可能整份返回。服务器规则 IPC 仍使用完整权威事务状态，也仍生成完整内部快照；本轮没有假称完全消除了快照。

6. **消除拾取前额外发送剩余移动的串行往返。** 新服务在 character 回复协商 `command_movement_revision=1`；客户端暂停发起新的移动请求，等已发请求收尾后，将直到操作边界的剩余输入与交互一起提交。服务器在同一事务复用原移动验证、时间额度、区域与碰撞路径，再执行交互。额度不足仅确认输入前缀，不产生回执/物品/交互结果，客户端沿同一 ID 继续；重试不重复移动或奖励，失败沿原事务回滚。旧服务无此协商字段时仍用原先移动确认流程。

7. **相邻建筑重复重建。** 建造或设施状态同步原来会重建周围 160 范围的所有建筑，一次应用实测创建/待删 32 个根节点。联机恢复现保留未变化的邻近家具和碰撞体；地板按最新邻居数据重绘，边向结构连接仍保留必要重建，真正改变/删除的设施维持原刷新。此开销含后续引擎清理，不能仅以 apply_snapshot 返回时间代表全部成本；也不能认定它解释了所有长帧。

## 测试方法与计时边界

- Godot 4.7.2，Compatibility/NVIDIA RTX 3060，真实 1280×720 窗口；相同世界初态（88 建筑）、人物位置、测试物品与操作顺序，单人及双人。双方不同掉落/背包/制作/建造，同时同物竞争；移动期间发出这四类命令，普通快照持续更新。多余阻挡建造/距离拒绝单独记，不混入成功操作分位数。
- 云端一次性副本，经 SSH 转发的 TLS 连接访问，正式数据只读。不是生产入口验收，也不是裸 UDP/ICMP 测量；SSH 的复用及网络变化会影响往返，不能把所有前后差值都归因代码。
- 客户端 `Time.get_ticks_usec`、服务端 `perf_counter_ns` 分别相减，只关联唯一 request_id，绝不相减两台机器系统时间。HTTP 发送/收完是应用层观察点，`wfile.write` 完成是交给本机传输栈，不冒充网卡实际出包时间；未测单向传播时间。
- 字节数为实际 UTF-8 HTTP 请求体、gzip 响应体与解压 JSON 长度，不含 HTTP 头、TLS、SSH/IP 链路开销。频率为各连接实际观察频率，不是设置值。
- 第一帧记录 `RenderingServer.frame_post_draw`，代表结果提交到渲染完成，不等同显示器光子出现；包括完整状态应用后的 UI。帧耗来自真实窗口逐帧时间，不用后台规则耗时替代。
- 冷启动/初始化与进入世界后的帧耗分开。6 次/人拾取、6 次制作、12 次移格，建造因当前地形阻挡成功数不同，实际样本数见数据；P95 用线性插值，样本规模不支持长期尾部稳定性结论。
- 原始含测试凭证的文件在被忽略的 private/；可公开的汇总见 summary.json、lifecycle.csv、consistency.json、measurements.md。中间轮次保留作排查；早期 after-single-final 曾与另一个本地规则测试短暂重叠，其后单独重跑 final2。该版本双人确认长尾仍未改善，因此继续实现有序移动合并，其后又定位邻近节点重建，最终采用 after-single-entities / after-double-entities；另列 before-single-ui / after-single-ui 面板可见对照；没有在最终原生测量期间并跑其他规则测试。

## 主线程与实体恢复的实际结论

解压、JSON 解析、增量合并、load_state、界面更新均在客户端主线程。原实现已经按建筑变化行刷新，也保留未变化的动物/建筑显示节点；不能说每次都把整个世界删掉重建。实际仍有遍历、深复制、全组件验证、营地恢复和显示同步。本轮缓存削减其中已测得的重复验证；没有引入后台线程去修改场景树，也没有在未验证完成时先发物品。

`network_sync_world_v3` 记录每次应用新增/待删除的对象根节点，最终轮次还统计新根节点子树内碰撞对象数（早期轮次该项未测）；item_service 单独量 inventory.changed 同步 UI 回调；真实帧记录收到响应/应用附近的帧耗，以及引擎 physics/process 监控值。后两项是整帧指标，**无法单独精确归因 PhysicsServer 内部碰撞注册耗时**。节点更新花费包含在状态应用及其阶段，不能把它们与整帧物理耗时再次相加。

## 未关闭的问题

- 普通交互 P95 ≤150 ms 尚未达到，不应以消息缩小或规则测试通过宣布完成。
- 已将剩余移动与交互合并，但仍要等待已在途的移动请求结束，额度不足也需后续请求补齐；并没有把这段等待归零。旧服务器兼容分支仍是先确认移动再交互。
- 命令仍依赖服务端完整事务状态的 IPC 恢复/序列化与规则执行；同世界事务排队、物理等待及某些世界推进仍是长尾来源。HTTP 分连接并不等于规则宿主并行。
- 组件变化时仍全组件传输/应用；本轮没有实体字段补丁、巨量初始场景分批加载验收，也没有把主线程场景应用全部搬走。初始重复数据已消除，但大批初次节点注册仍需单独处理。
- 帧时间 P95 改善不代表已消除长帧；最大帧及同步附近长帧照实保留在 measurements.md。真实生产入口、长时间多人世界和不同网络环境尚未验收。

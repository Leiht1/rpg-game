# 联机延迟全路径审计 V1

2026-10-28。结论：延迟问题仍未解决，本轮建立了分段基线与后续修改清单，**没有修改联机实现**。本地覆盖当前全部有效命令入口；公网覆盖核心操作及持续负载，不将其称为全部功能的公网验收。

## 测试条件与数据

- 源码基准 `2d7dd86`；Godot 4.7.2，Windows 默认 1280×720 原生窗口。客户端仅包含本轮界面修订，服务器源码、协议、同步频率、超时和事务规则没有修改。
- 用户提供 TEST-002/TEST-004 的激活凭证后，创建两个临时账号及一个独立 1536 格云端测试世界。只操作这两个测试角色，未登录、迁移或改写原有玩家角色；没有 SSH 操作、停服、部署或发布。临时测试账号/世界保留供下一轮对照，登录资料仅在本机忽略目录。
- 公网端点为当前配置指定云服。没有 SSH，因此没有核对云端运行文件 SHA、读取云端 CPU/磁盘/锁等待或请求级服务器分段计时。测试证书从指定端点取得后固定在独立测试配置，不能冒称来自原客户端证书的独立指纹核验；项目配置未被替换。
- 公网分开运行单人、双人两组，各含 120 秒持续操作及进入、面板、移动、收尾阶段，共 10,685 个 API 调用。保留游戏原移动/角色轮询/世界快照节奏，持续交替整理背包和攻击。两个客户端在同一电脑；没有与本地规则负载测试重叠运行。
- 本地严格 TLS、持久连接、gzip、原 Service + 原 Godot 规则进程 + SQLite，60 个有效操作情境各 6 轮，1/2/4 **调用方**共 2,520 个请求，35 个有效命令入口均有成功样本；另有普通快照。四调用方不等于公网四个真实客户端。具体操作、成功/拒绝数与分位数见 [coverage.csv](coverage.csv)。
- [summary.json](summary.json)保留汇总及远端观察；[restore-stress.json](restore-stress.json)保留完整地图恢复专项。逐请求 ID、分段、HTTP body 大小及客户端帧记录保留在本目录的 `controlled*-tls.json`、`public-*.json`，为本机原始测量记录，不含账号密码或激活凭证，按日志规则忽略版本控制。

计时定义：操作确认是入队到**该命令**完成并应用结果；请求往返/解码包含客户端 HTTP 泵与解压，不能称为纯线路 RTT。面板单独测至绘制；远端动作另测至观察端出现。P95 使用排序后 `floor((n-1)*0.95)`。不把制作规定时长、正常失败原因、共享对象争用拒绝当成网络超时。

这几段的 P95 不能相加作为端到端 P95：它们不一定来自同一个请求。HTTP 通道自身排队和 HTTP 前的命令排队分别保留在汇总中；本组后者主要是等待已在途快照。源码中的 interact 还需要等待对应移动确认，本组没有量化其分摊。

游戏通道 HTTP body 中位约 6.6KB，解压后 JSON 中位约 129KB；这是 HTTP body，不是包含 TCP/TLS/报文头的线上总字节数。本场景没有证据支持“单纯公网带宽不足”是主因，也不能据此排除复杂世界下的带宽问题。

冷启动单列：独立世界创建请求 15.209 秒，首次角色进入请求 18.279 秒，第二角色进入 0.694 秒；不含客户端完整场景绘制时间。不能拿热进入的约 90ms 代替首次进入表现。

最终 2,520 请求中 HTTP 500 为 0。拒绝包括同一地面物品被抢先拾取、重复领取、共享箱过期来源、作物已被收获、动物刚被喂食、已有建筑等。拒绝延迟和成功延迟分别记录，不以拒绝的快速响应降低成功操作分位数。

本地矩阵按测试夹具恢复场景再发请求，包含物品重新出现/消失、共享对象竞争、库存与营地复位。因此它刻意覆盖恢复与重新加载路径；高分位尤其包含这些成本，**不是正常连续游玩的总体分布**。其中一次拾取夹具总计约 926ms，约 922ms 在 Godot IPC、约 0.95ms 在本地 SQLite 序列化/提交。这只定位该本地恢复场景，不能推定云端磁盘耗时。

## 本机反馈与远端显示

重复远端观察轮次中，12 次攻击均在另一端看到：本机起手约 7–9ms，另一端首次观测约 118–264ms。这是两个同机窗口经公网服务器、以同一系统时钟关联的短样本，不是跨机器时钟同步验证。

但前一轮 6 次中只观测到 5 次，缺失的那次观察端仍在运行；原始记录保留于 `exploratory-remote/`。重复未复现不等于修复，当前不能区分短状态未广播、到达过晚、未呈现或测试采样遗漏。已列为下一轮需追查的偶发短动作同步问题。重复轮次还记录了 poll 返回的攻击状态，以便后续逐层关联。

## 已发现的结构与下一步修改顺序

以下是对当前源码及本轮证据的判断；没有改动对应实现，也没有宣称已完整定位云端长尾根因。

1. **先消除操作被普通快照拖住。** `network_game_world.gd.sync_server` 的 `requesting` 串行调度与 `network_client.gd` 的 game 通道同时承载命令和快照。已有四通道连接不代表命令/快照互不阻塞。公网 HTTP 前 P95 排队可到约 106ms，是可以单独优化和验证的量。
2. **减少权威请求的场景恢复/等待。** `network_game_worker.gd` 中，普通背包移格已有例外，其余大量命令仍等待 process/physics 帧及视口准备。`gameplay.py.apply` 每次合并并恢复共享/个人状态，服务端在同一事务期间还可能先推进其他角色。应先测量并精简无空间查询命令，再评估常驻世界与固定模拟步，避免继续逐条加工具或物品补丁。
3. **把短动作同步作为事件检查。** 只有“当前仍在攻击”的快照可能不足以可靠表达一次已经发生的短动作；需要追踪动作编号、起止时刻、发送/接收/显示，而不是只证明本机预演出现。此前 1 次未观测必须继续核实，不能凭本轮 12 次正常关闭问题。
4. **缩小同步和应用范围。** 当前正文中位约 129KB，gzip 后不大，但每次仍解析/恢复整份快照，实测应用约 9ms。后续按变化发送库存/身体/附近实体，并缓存静态状态；同时保留物品去重、失败回滚和共享对象权威。不能把未落盘的乐观显示说成已提交。
5. **独立处理冷启动与历史长尾。** 冷建世界/角色已是十几秒量级；下一轮需要云端请求 ID 关联的锁等待、规则恢复/推进、落盘和发包计时，及真实复杂存档副本下的对照。现在没有这些云端内部数据，不能用本地快速样本证明云服已经正常。

验收应分开要求本机起手、权威确认与远端可见，按同一数据和负载比较 P50/P95/最大/超 1s 次数；采集、制作和门动画的规定时长单列。目标是输入及时反馈、权威正确提交、其他玩家及时看到，不承诺物理上的零网络延迟。

## 查阅资料

- [Godot 4.7 官方联机文档](https://docs.godotengine.org/en/4.7/tutorials/networking/high_level_multiplayer.html)：可靠/不可靠传输与独立通道用于不同消息；协议/通道选择应结合消息时效和可靠性。
- [Glenn Fiedler：State Synchronization](https://gafferongames.com/post/state_synchronization/)：以输入和部分状态同步、对象间更新仍继续模拟、按优先级节省状态更新；作者同时说明这种方法有误差和纠偏成本。
- [Steamworks 官方网络接口说明](https://partner.steamgames.com/doc/features/multiplayer/networking)：区分可靠与不可靠消息及连接式/消息式接口。

结合本项目的推断：先处理已测出的排队、规则恢复和短动作表达，再决定是否引入实时传输/推送；直接把 HTTP 换成 UDP 并不会自动消除 Python 事务和 Godot 请求处理内部的串行等待。上述资料不是“必须整体改成某一协议”的依据。

## 口径修正与未测边界

- 第一轮 `public-native-*.json` 的部分“确认时间”等待了命令完成之后的下一次后台快照，不能作为准确操作确认值。保留探索记录，但最终操作确认表只采用按具体 request_id 完成计时的持续轮次；API 往返记录仍仅供参考。
- 夹具开发初跑曾有脚本启动/夹具设置问题、限流与不合法门位置/睡眠拥有者导致的拒绝；修正了测试设置和请求节奏，最终矩阵没有限流拒绝或 HTTP 500。没有修改生产校验来让测试通过。
- 未测公网四人、异地双机、长时间弱网/丢包、正式 ht 世界的隔离副本及所有功能的公网完整流程；没有云端内部排队/CPU/RSS/磁盘计数。源代码入口覆盖不等于这些范围已经通过。
- 期间只使用两个测试账号；临时账号密码、激活凭证、会话、证书测试配置在 `reports/.tmp/`，不会进入报告或 Git。结束后所有测试客户端与私有服务/规则进程均已退出，两个测试角色离开在线大厅。没有自动继续任务。

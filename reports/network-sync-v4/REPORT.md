# 联机同步 V4：移动版本、事务分流与界面等待

2026-10-29。本轮为本地候选；云端仅运行一次性隔离测试副本，没有替换正式服务、发布客户端、提交或推送。正式 Data 只读挂载，测试账号、世界与进程独立。其他工作区修改保留。

## 实施与边界

1. **移动依赖**：协商 `position_revision=1` 后，交互携带位置版本和点击时不可变的输入前缀，直接发送，不再等正在进行的移动请求。服务器仍用原输入编号、时间额度、地形和碰撞验证；缺少输入则补算，已领先则在一秒内的权威位置检查点重算该次交互，再恢复当前位置。晚到的旧移动应答不回退客户端预测。额度未满足仍可明确返回待重试，不靠客户端坐标放行。旧客户端保留原兼容路径。
2. **事务分流**：背包 8–39 格之间移格、拆分、销毁及整理在严格条件下走轻事务，复用原 Godot 库存规则，在共享世界锁外计算，提交前比较所有个人依赖；冲突重验，保存失败回滚，重复请求不重复发放。装备、使用物品、活跃制作/钓鱼/战斗、销毁当前灯具等仍走原事务。修正“保留灯具 ID 即阻断所有轻事务”和轻事务遗漏待处理交互登记的问题。轻事务捕获、提交、持久化仍需共享锁，不能称为完全消除争用。
3. **帧末应用**：接收后先发出权威结果已到达信号，再排入待应用队列；同代后台快照合并，命令按序应用，过期后台状态丢弃，轻事务仅恢复库存。`call_deferred` 在主循环末尾应用，不额外等一整帧。网络解码仍在主线程，并未新增网络线程；确认、状态应用和首帧指标分别保留，不能换统计口径制造改善。
4. **面板单独排查**：分别记录背包、制作、建造从打开到首帧的耗时，每类十二次。修正空闲切换制作/建造时仍发送 `craft_cancel` 的问题；存在权威任务或排队中的制作请求时仍保留取消，避免竞态。移除切换模式后重复构建一次制作列表。
5. **区块缓存**：容量保持 64，由插入顺序淘汰改为命中后更新顺序的 LRU。用 643 次、超过容量的固定路线与热点返回测试，直接调用真实不可变规则分布生成并核对淘汰后结果一致。数据见 supplement.json；这是规则生成耗时，不是玩家操作确认耗时，不能证明 64 对任意人数长局都足够。未新增猜测性预取。
6. **制作断线恢复**：保留未确认时 99.9% 上限，权威任务清空才结束；真实测试还发现控件默认步长会将 .999 取整为 1，已将步长改为 .0001，使实际控件也不提前满格。恢复任务时同时恢复所属工作台标识。真实客户端任务进行中结束连接，再以新进程重新登录、恢复和绘制，检查原料仅扣一次、产物仅发一次，继续等待后无重复发放。当前断线专项用徒手配方，不等同覆盖所有工作台、半包故障或服务器崩溃。

“纯任务”没有被一概划入轻事务：制作会扣材料、推进身体与工作台状态，任务进度可能发奖励，不能因名称看似个人操作就跳过原验证。当前没有可直接拆出的纯只读空间查询接口；`game_snapshot` 可能推进世界并修改选中格，未将它假称为并发只读。因此三类事务的完整分流尚未完成。

## 测试口径与数据

冻结本轮开始时的 V3 工作树作为 before；前后同一初始测试世界、88 个建筑、相同库存、种子与动作。Godot 4.7.2，1280×720 实际渲染窗口；单人、双人不同对象、同对象争抢、移动中交互、快照期间背包操作、面板打开及新进程恢复。云端隔离副本，经同一 SSH TLS 转发链路。普通确认包含权威状态应用；另列权威回复已解析和结果首帧，制作的设计等待时长不计入启动命令。

最终数值见 [测量表](measurements.md)、[逐请求生命周期](lifecycle.csv)、[汇总](summary.json)、[界面/缓存/服务分段](supplement.json)、[一致性](consistency.json)。中间 after-single-v4、after-double-v4 属于发现遗漏前的迭代，未混入最终对照。两端各用单调时钟测量本机时段；HTTP 总往返与服务端嵌套阶段分列，没有直接相减两机器系统时间。

逐成功请求表只计接受的普通操作；supplement.json 的服务器分段按操作类型收集该轮所有调用，包含争抢、明确业务拒绝与重试，两者分母不同。重试次数单列于 lifecycle.csv，发送前时间可能含前次尝试，不伪装成纯调度开销。

### 缓存压力（规则生成，不是交互延迟）

|策略|命中率|命中生成 P50/P95/max|淘汰后重新生成 P50/P95/max|
|---|---|---|---|
|FIFO / 64|378/643，58.79%|0.05 / 0.11 / 0.20|53.58 / 64.61 / 71.98|
|LRU / 64|395/643，61.43%|0.04 / 0.14 / 0.28|48.97 / 59.25 / 69.01|

缓存生成在未命中时仍有几十毫秒成本；LRU 只改善该路线的热点保留，不消除重新生成，也不证明上限最优。生成算法没有变化，单次未命中耗时的差值不能归因于 LRU。两轮重新生成结果一致。

### 已运行验证

- 完整规则 36 项通过（主要实现完成时）；最后的优先级登记、灯具守卫及 feature gate 修订后，重跑事务/版本/幂等/回滚和并发冲突两项，2/2 通过。
- 真实 TLS 旧客户端、丢失回复、并行基线及恢复协议 1/1 通过。
- 最终各原生阶段库存守恒、同对象唯一获胜、双人建筑 ID/数量一致、新进程恢复检查通过；具体成功数、交叠请求数和队列长度见 consistency.json。普通单/双人无持续积压；面板切换可能出现短暂排队，不能写成所有时刻队列恒零。
- 制作断线专项最初失败：控件默认 step 把 .999 取整到 1。将 step 设为 .0001 后重新运行，实际控件值小于 1，未提前发放奖励。
- 制作在途关闭后新进程恢复通过，产物 30→33，再次等待后不重复。恢复后等待中的任务采样数 0；如果为 0，表示初始全量恢复时服务端已结算，并非验证了重连后长时间继续显示进度。

面板问题单独记录于 [UI_LATENCY.md](UI_LATENCY.md)，包括没有改善的指标。

## 尚未解决

- 单人拾取发送前等待中位数 96.13→2.46 ms，证明预等移动已拆除；拾取确认 P95 361.08→303.61 ms，背包移格 306.63→177.75 ms。但制作 282.71→337.46 ms、建造 300.80→323.55 ms，四类合计 P95 仍约 322 ms。不能把已拆掉的串行等待说成全部尾延迟根因。
- 单人背包规则 IPC 中位数 47.50→5.02 ms、服务端整段 71.56→24.95 ms；世界写操作仍有约 63–69 ms 的规则 IPC 中位数，其内还包含完整恢复、场景等待、规则推进与结果生成。一次代表性拾取确认 221.39 ms，其中 HTTP 发出至收完 191.96 ms（嵌套服务器业务 109.57 ms），本地权威应用 15.47 ms。HTTP 残差还含链路与客户端轮询，不能全部算纯网络；没有进一步把 IPC 总耗时归给某个单一函数。
- 世界写操作仍经过完整规则宿主与共享世界事务；个人轻事务提交仍可能被它阻塞，任务及空间查询未完成全面分流。
- 主线程仍负责解码和必要世界状态恢复；帧末合并改变应用时机，不保证单次恢复变便宜。不能以早到信号取代玩家实际看到结果的时间。
- 同步附近帧 P95 单人 41.35→41.21 ms、双人 43.39/42.79→42.09/42.04 ms，改善很小；全程仍出现超过 100 ms 的长帧。面板组全程帧 P95 反而由 33.43 升到 34.81 ms，主线程长停顿未关闭。
- 本次有限样本与波动网络无法证明多人长局尾延迟稳定，缓存也未做所有人数/路线的容量寻优。
- 轻事务复用每角色常驻库存规则宿主；本轮只验证一、两名角色，尚未测量更多在线角色时新增进程的内存/CPU容量。
- 150 ms 是验收目标，需以最终测量判断；未达即继续保留问题，不写成联机性能验收通过。
